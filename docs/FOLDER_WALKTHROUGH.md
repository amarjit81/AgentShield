# Understanding AgentShield, folder by folder

This walkthrough explains code that exists today. The implementation guide is
the fuller technical record. Learn one request flow first instead of memorizing
every file at once.

## 1. The top-level map

| Folder | What it does | Start here |
|---|---|---|
| `src/` | React dashboard: what the user sees and clicks | `src/App.jsx` |
| `backend/` | Express API: validates requests, evaluates refund rules, stores data, saves reviews | `backend/src/routes/actionRoutes.js` |
| `docs/` | Explanations, current limitations, and verification history | `docs/IMPLEMENTATION_GUIDE.md` |
| `node_modules/` | Installed frontend libraries; generated by npm | Usually do not edit |
| `dist/` | Generated frontend production build | Rebuilt with `npm run build` |

`package.json` at the root belongs to the frontend. `backend/package.json`
belongs to the backend. Each has its own commands and dependencies.
`vite.config.js` forwards frontend `/api` calls to Express on port 3000.
`backend/.env` holds local database configuration and is ignored by Git.

## 2. First lesson: backend/src

Think of the backend as a team with small, separate jobs:

| Folder / file | Job | Concrete example |
|---|---|---|
| `server.js` | Opens the HTTP port | Starts listening on port 3000 |
| `app.js` | Assembles Express, JSON parsing, routes, error handling | Reads JSON and returns generic errors |
| `routes/` | Connects a URL and method to a handler | POST `/api/actions/:id/review` calls `reviewAction` |
| `schemas/` | Checks incoming data with Zod | A review must say APPROVE or REJECT |
| `controllers/` | Coordinates the steps and sends the response | Validate review, update stored status, return HTTP 200 |
| `services/` | Makes domain decisions | Refund limits produce ALLOW, REQUIRE_APPROVAL, or BLOCK |
| `repositories/` | Reads and writes database records | Only update a request whose status is PENDING_APPROVAL |
| `lib/` | Shares infrastructure helpers | One reusable Prisma database client |

The review endpoint does not re-run refund policy. The original policy decision
already exists; review moves a pending request to an approved or rejected state.
OPA/Cedar would eventually sit behind the policy service if adopted; neither is
implemented today.

## 3. Trace the feature added on 2026-10-09

1. A user clicks Approve or Reject in `src/App.jsx`.
2. `src/services/actions.js` posts the decision to the review URL.
3. `backend/src/app.js` parses JSON and forwards it to the action router.
4. `backend/src/routes/actionRoutes.js` selects the controller.
5. `reviewAction()` in `controllers/actionController.js` validates ID and body
   using `schemas/actionSchema.js`.
6. `reviewPendingAction()` in `repositories/actionRepository.js` conditionally
   writes the new status through the shared Prisma client.
7. The controller returns the saved status, or a validation/not-found/conflict
   error. The dashboard changes state only after a successful response.

Example: an ₹8,000 refund starts as PENDING_APPROVAL. Approve changes the stored
status to APPROVED. Another approval or rejection then gets HTTP 409. Its
original policy outcome remains REQUIRE_APPROVAL, explaining why it was reviewed.

This saves a review decision, but does not yet verify that the caller is a
manager. Refund execution and the approval snapshot now live in the backend. See the implementation guide for the execution and audit routes added after this initial walkthrough.

## 4. Other backend folders

- `backend/prisma/schema.prisma`: the database blueprint. ActionRequest holds the
  requested action and current status; PolicyDecision holds the rule outcome.
- `backend/prisma/migrations/`: SQL history that creates or changes the database.
- `backend/test/actions.test.js`: API/database checks, including competing reviews.
  Its cleanup deletes request records, so run it only against an isolated test DB.
- `backend/node_modules/`: installed backend libraries; generated by npm.

## 5. Suggested learning order

Read `routes/actionRoutes.js` first, then follow its `reviewAction` import to the
controller. Read the schema and repository functions it uses next. Finally,
look at the matching tests and the frontend HTTP helper. Later lessons can cover
React state, database relations, and execution enforcement in more depth.
